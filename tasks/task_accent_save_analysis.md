# Анализ: сохранение набора акцентов при переключении имени

> **Статус: найдена и исправлена настоящая корневая причина** (девятое
> исправление) — баг в `parseTickAccents()`, живший с самого первого коммита
> тикающих акцентов. Ждёт проверки на устройстве.
>
> Обходное решение: [task_activity_presets.md]
> Долгосрочное решение (устранить дублирование хранилищ): [task_settings_to_sqlite.md]

## Хронология попыток исправления

### Коммит `a2feed5` — первое исправление
**Проблема:** диалог TickSettings закрывался кнопкой «Закрыть» без вызова
`saveCurrentNameToggles()`. Изменения применялись через `updateTickAccents`
на каждое изменение внутри диалога, но явного сохранения при закрытии не было.

**Исправление:** кнопка → «Сохранить», добавлен явный `saveCurrentNameToggles()`
в `onSave`.

---

### Коммит `6fd1ad6` — второе исправление
**Проблема:** `loadNameToggles` при загрузке имени с сохранёнными акцентами
перезаписывал глобальный ключ `preferencesManager.tickAccentsJson`:
```kotlin
preferencesManager.tickAccentsJson = it   // ← перезаписывал глобальный ключ!
```
При возврате к имени без своих акцентов (`tickAccentsJson == null`) читался
уже «испорченный» глобальный пресет.

**Исправление:**
- `tickAccentsJson != null` → восстанавливать `_tickAccents.value`, НЕ трогать
  `preferencesManager.tickAccentsJson`.
- `tickAccentsJson == null` → явно читать `preferencesManager.tickAccentsJson`.
- `parseTickAccents("[]")` → больше не сбрасывается к DEFAULT (откат только
  для полностью битого JSON без `[`).

---

### Коммит `3eabe79` — третье исправление

Найдены три корневые причины, по которым акценты сбрасывались к DEFAULT при
переключении имени:

#### Причина 1: `saveSession` создаёт entity без togglesJson/accentsJson
```kotlin
// Было в saveSession:
sessionNameDao.insert(SessionNameEntity(name = name))  // togglesJson=null, accentsJson=null
```
Когда пользователь сохраняет сессию с именем впервые, entity в `session_names`
создаётся с null-полями. При последующем `loadNameToggles` для этого имени код
попадает в `else`-ветку, там `preferencesManager.getNameToggles` возвращает null
(миграция уже выполнена), и ничего не применяется — акценты остаются от
предыдущего состояния (при старте приложения это DEFAULT).

#### Причина 2: Заражённый глобальный ключ как fallback в IF-ветке
```kotlin
// Было в loadNameToggles (IF-ветка):
_tickAccents.value = parseTickAccents(
    entity.accentsJson ?: preferencesManager.tickAccentsJson  // ← заражённый глобал!
)
```
Если `accentsJson == null` (entity создана через saveSession), читался глобальный
ключ. Этот ключ перезаписывался при каждом `updateTickAccents` любого имени,
т.е. содержал акценты последнего редактировавшего имени, а не DEFAULT и не
акценты целевого имени.

#### Причина 3: `updateTickAccents` не сохранял per-name акценты в SharedPreferences
```kotlin
// Было в updateTickAccents:
preferencesManager.tickAccentsJson = serializeTickAccents(accents)  // только глобал
saveCurrentNameToggles()  // DB — OK, но SharedPreferences per-name — нет
```
Метод `preferencesManager.saveNameAccents(name, accentsJson)` (введённый ранее)
не вызывался, поэтому `preferencesManager.getNameAccents(name)` в fallback-цепочке
всегда возвращал null.

### Четвёртое исправление (текущее)

Три предыдущих исправления не решили проблему, потому что оба источника null-entity
не были устранены.

#### Причина 4а: `saveSession` создаёт entity без togglesJson/accentsJson

```kotlin
// Было:
sessionNameDao.insert(SessionNameEntity(name = name))  // togglesJson=null, accentsJson=null
```

Когда сессия сохраняется с новым именем, `saveSession` создаёт entity с
`togglesJson=null, accentsJson=null`. При следующем `loadNameToggles` ELSE-ветка
применяет DEFAULT и **записывает его в DB**. Отныне IF-ветка всегда читает DEFAULT.

**Исправление:** `saveSession` теперь сохраняет текущие toggles и акценты:

```kotlin
sessionNameDao.insert(
    SessionNameEntity(
        name = name,
        togglesJson = serializeCurrentToggles(),
        accentsJson = serializeTickAccents(_tickAccents.value)
    )
)
```

#### Причина 4б: сид v1 пропускает существующие entity с null accentsJson

```kotlin
// Было в seedActivityPresetsIfNeeded:
if (sessionNameDao.getByName(name) == null) {
    sessionNameDao.insert(...)  // иначе — ничего
}
```

Если пользователь ранее сохранял сессии с именем пресета («дыхание медведя» и т.п.),
entity уже существует с `accentsJson=null`. Сид видит непустой результат и пропускает
вставку. В итоге ELSE-ветка записывает DEFAULT вместо пресетных акцентов.

**Исправление:** сид v2 обновляет существующие entity с `accentsJson=null`:

```kotlin
when {
    existing == null -> sessionNameDao.insert(...)           // v1: вставить новую
    existing.accentsJson == null -> sessionNameDao.update(   // v2: починить старую
        existing.copy(accentsJson = serializeTickAccents(preset.accents))
    )
}
```

Новый флаг `activityPresetsSeedV2Done` гарантирует однократный запуск миграции.
Пользовательские акценты (accentsJson != null) при этом не перезаписываются.

## Применённые исправления (StopwatchViewModel.kt)

### 1. `updateTickAccents` — сохранять и в per-name SharedPreferences
```kotlin
fun updateTickAccents(accents: List<TickAccent>) {
    _tickAccents.value = accents
    val accentsJson = serializeTickAccents(accents)
    preferencesManager.tickAccentsJson = accentsJson
    val name = _currentName.value.trim()
    if (name.isNotBlank()) {
        preferencesManager.saveNameAccents(name, accentsJson)
    }
    saveCurrentNameToggles()
}
```

### 2. `loadNameToggles` IF-ветка — правильная fallback-цепочка
```kotlin
// Стало:
_tickAccents.value = parseTickAccents(
    entity.accentsJson
        ?: preferencesManager.getNameAccents(name)   // per-name legacy
        ?: serializeTickAccents(DEFAULT_TICK_ACCENTS)  // явный DEFAULT, не глобал
)
```

Аналогично в `if (toggles != null)` else-ветки:
```kotlin
val accentsJson = preferencesManager.getNameAccents(name)
    ?: toggles.tickAccentsJson
    ?: serializeTickAccents(DEFAULT_TICK_ACCENTS)  // было: preferencesManager.tickAccentsJson
```

### 3. `loadNameToggles` ELSE-ветка — обработка entity с null togglesJson
Добавлена ветка `else` (когда `toggles == null`), которая раньше была NO-OP:
```kotlin
} else {
    // Entity из saveSession: togglesJson=null, нет legacy префов.
    val nameAccentsJson = preferencesManager.getNameAccents(name)
    _tickAccents.value = if (nameAccentsJson != null) {
        parseTickAccents(nameAccentsJson)
    } else {
        DEFAULT_TICK_ACCENTS
    }
    // Сохраняем в DB, чтобы следующий load пошёл по быстрому IF-пути.
    val togglesJson = serializeCurrentToggles()
    val accentsJson = serializeTickAccents(_tickAccents.value)
    val dbEntity = entity ?: SessionNameEntity(name = name)
    if (entity != null) {
        sessionNameDao.update(dbEntity.copy(togglesJson = togglesJson, accentsJson = accentsJson))
    } else {
        sessionNameDao.insert(dbEntity.copy(togglesJson = togglesJson, accentsJson = accentsJson))
    }
}
```

## Пятое исправление — «Проблема 1» + бэкап (см. [task_settings_to_sqlite.md])

`updateCurrentName` теперь вызывает `saveCurrentNameToggles()` для уходящего
имени перед переключением (только если это было известное имя — иначе каждый
символ при вводе нового имени создавал бы мусорные entity). `loadNameTogglesBody`
IF-ветка больше не читает legacy SharedPreferences-ключ как fallback.

Отдельно найден и исправлен независимый источник сброса: `BackupManager`
восстанавливал `session_names` без `togglesJson`/`accentsJson` (голые имена),
а `BackupWorker` вообще не передавал `sessionNameDao` — то есть любой
бэкап/restore (особенно автоматический) сбрасывал акценты всех имён.

**Статус: ждёт проверки на устройстве** (сборки только через GitHub Actions).

## Шестое исправление — акценты пресетов не применялись при переключении

**Проблема:** при переключении на имя, совпадающее с одним из `ACTIVITY_PRESETS`
(«дыхание медведя», «дыхание полоза», «дыхание сокола», «задержки на выдохе»,
«дерево жизни»), вместо акцентов пресета показывался обычный `DEFAULT_TICK_ACCENTS`
(1s TICK, 8s TOCK/BELL, 60s CHIME, 300s GONG).

**Причина:** связка «имя пресета → его акценты» существовала только в одноразовой
миграции `seedActivityPresetsIfNeeded()`, которая гарантированно выполняется один
раз за установку (флаги `activityPresetsSeedDone/V2/V3`). Если запись для имени
пресета создавалась или оставалась «испорченной» (accentsJson = null или равен
DEFAULT) уже ПОСЛЕ того как эти флаги стали `true`, никакой код больше не сверял
имя со списком пресетов — `loadNameTogglesBody` просто ставил `DEFAULT_TICK_ACCENTS`.

**Исправление:** добавлена `findActivityPresetAccents(name)` — сверка имени со
списком `ACTIVITY_PRESETS` по `nameRu/nameEn/nameZh`, вызываемая:
- в `loadNameTogglesBody` при каждой загрузке (самовосстановление: если
  `accentsJson` записи пуст или равен DEFAULT, а имя — пресет, акценты пресета
  применяются и сохраняются заново, не дожидаясь одноразового сида);
- в `saveSession` при первом создании записи для нового имени (чтобы `Reset`
  сразу после ввода имени-пресета без предварительного переключения тоже
  создавал запись с акцентами пресета, а не с текущими/дефолтными).

Одноразовый `seedActivityPresetsIfNeeded()` оставлен как есть (избыточен, но
не вреден).

**Статус: ждёт проверки на устройстве.**

## Седьмое исправление — гонка между сохранением старого имени и загрузкой нового

**Проблема:** шестое исправление не помогло полностью. Воспроизведённая
последовательность на 0.23.0:

1. переключение на «Дерево жизни» — 2 акцента пресета (OK)
2. переключение на «Сокол» — OK
3. переключение на «Дерево жизни» — акценты DEFAULT (= то, что было у «Сокол»)
4. переключение на «Сокол»
5. переключение на «Дерево жизни» — снова 2 акцента пресета (OK)
6. «Дерево жизни» — добавление акцента → 3 акцента
7. переключение на «Сокол»
8. переключение на «Дерево жизни» — снова DEFAULT

Нестабильность (то OK, то нет при одних и тех же действиях) указывала на гонку,
а не на детерминированную логическую ошибку.

**Причина:** `saveCurrentNameToggles()` (сохраняет акценты имени, которое
покидаем) и `loadNameTogglesBody()` (загружает акценты нового имени, включая
самовосстановление пресета из шестого исправления) запускались как две
независимые корутины через `viewModelScope.launch { ... }`, ничем не
синхронизированные между собой. `_tickAccents` — общий `MutableStateFlow`.

При быстром переключении (что естественно при ручном тестировании подряд)
возможно, например, такое чередование:
- Уходим с «Дерево жизни» на «Сокол»: `saveCurrentNameToggles()` синхронно
  берёт `name = "Дерево жизни"`, но САМО чтение `_tickAccents.value` и запись
  в БД происходят уже внутри запущенной корутины — если в этот момент ещё не
  завершилась предыдущая загрузка/самовосстановление для «Дерево жизни»
  (например, ещё выполняется suspend-чтение из Room), `_tickAccents.value`
  может быть не тем, что должно принадлежать «Дерево жизни».
- Одновременно уже стартовала `loadNameTogglesBody("Сокол")` и могла успеть
  переписать `_tickAccents.value` на значение «Сокола» ДО того, как
  «сохранение Дерева» дочитает это значение — тогда в БД для «Дерево жизни»
  вместо его акцентов ошибочно запишутся акценты «Сокола» (не обязательно
  DEFAULT напрямую, но именно так объясняется наблюдение «Дерево == тому, что
  было у Сокола»).

Обе корутины никак не ждали друг друга и не были взаимно исключающими —
результат зависел от того, в каком порядке реально отработают их
suspend-точки (обращения к Room), то есть был недетерминированным.

**Исправление:** введён `nameSwitchMutex: Mutex`, через который теперь
проходят ВСЕ операции, читающие/пишущие `_tickAccents`/`session_names` при
переключении имени:
- `loadNameToggles(name)` — `viewModelScope.launch { nameSwitchMutex.withLock { loadNameTogglesBody(name) } }`;
- `saveCurrentNameToggles()` — чтение `_tickAccents.value` и запись в БД
  вынесены ВНУТРЬ `nameSwitchMutex.withLock { ... }` (раньше `_tickAccents.value`
  захватывался синхронно до `launch`, что и позволяло гонке возникать);
- начальная загрузка в `init{}` тоже обёрнута тем же мьютексом.

Поскольку `saveCurrentNameToggles()` для покидаемого имени всегда вызывается
(и, соответственно, встаёт в очередь на мьютекс) РАНЬШЕ, чем
`loadNameToggles()` для нового имени (порядок вызовов в
`updateCurrentName`/`selectNameFromHistory` не менялся), при последовательном
выполнении мьютекс гарантирует: сохранение старого имени дождётся завершения
ЛЮБОЙ предыдущей операции (в том числе ещё не отработавшего самовосстановления
пресета) и только тогда прочитает уже гарантированно правильное значение
`_tickAccents.value`, после чего загрузка нового имени начнётся не раньше, чем
это сохранение полностью завершится. Гонка исключена структурно, а не за счёт
таймингов.

**Коммит:** `6340952` («Версия 0.23.1»).

### Проверка на устройстве (0.23.1): бага воспроизводится, седьмое исправление не помогло

Точная последовательность действий от пользователя (имена — «Дерево»
[= «дерево жизни», пресет из 2 акцентов] и «Сокол»):

```
1. переключение на Дерево - 2 акцента из пресета (OK)
2. переключение на Сокола - OK
3. переключение на Дерево - акценты из DEFAULT (==Соколу)
4. переключение на Сокола
5. переключение на Дерево - снова 2 акцента из пресета (OK)
6. Дерево - добавление акцента - 3 акцента
7. переключение на Сокола
8. переключение на Дерево - снова DEFAULT
```

Наблюдение: поведение НЕ хаотично-случайное (что было бы ожидаемо от гонки
потоков), а чередуется предсказуемо — визит 1 OK, визит 3 (третье переключение)
BROKEN, визит 5 OK, визит 8 (после правки на визите 6) снова BROKEN. Это говорит
о детерминированной логической причине, а не о таймингах — введение
`nameSwitchMutex` (седьмое исправление) её не устранило, что дополнительно
подтверждает: гонка если и существовала, не была (единственной) причиной.

Требуется дальнейшее расследование этой детерминированной причины —
подозрение падает на `saveCurrentNameToggles()`, вызываемый при уходе с
имени: он пишет в БД для ПОКИДАЕМОГО имени, но нужно перепроверить, не
пишутся ли туда акценты, реально принадлежащие ДРУГОМУ (текущему на момент
записи) имени.

**Статус: воспроизводится, требуется восьмое исправление.**

### Восьмой шаг — диагностическое логирование вместо очередной вслепую-правки

Поскольку статический анализ кода (включая учёт `nameSwitchMutex`) не выявляет
механизма порчи, а гипотеза "гонка" не подтвердилась на практике, в
`StopwatchViewModel.kt` добавлено логирование через существующий `AppLogger`
(тег `AccentDebug`) в ключевых точках:
- `loadNameToggles`/`saveCurrentNameToggles` — постановка в очередь и момент
  реального захвата мьютекса/записи;
- `loadNameTogglesBody` — вход (что прочитано из БД, `presetAccents`), какая
  из веток сработала (`HEAL_PRESET`/`USE_STORED`/`LEGACY_TOGGLES`/`FRESH`),
  выход (итоговое значение `_tickAccents`);
- `updateTickAccents` — ручное редактирование акцентов.

**Коммит:** `b46b5e1` («Версия 0.23.2», диагностическая, версия не влияет на
поведение, только добавляет логирование).

**Статус: ждёт лога с устройства для точной диагностики.**

### Как собрать логи (v0.23.2+)

Механизм логирования — существующий `AppLogger` (файл `laplog.log` в
`filesDir`), управляется с экрана **«Резервные копии»** (нижняя навигация,
4-я вкладка, иконка Backup).

1. Установить APK версии 0.23.2 или новее (собирается через GitHub Actions
   после пуша в `main`).
2. Открыть вкладку **«Резервные копии»**.
3. В карточке **«Логи приложения»**:
   - нажать **«Очистить логи»** — чтобы в файле не было шума от предыдущих
     тестов;
   - включить чекбокс **«Записывать лог в файл»**.
4. Вернуться на секундомер и повторить точную последовательность
   переключений из раздела «Проверка на устройстве (0.23.1)» выше (шаги 1–8:
   Дерево → Сокол → Дерево → Сокол → Дерево → правка акцента → Сокол →
   Дерево), фиксируя, на каком шаге акценты снова стали DEFAULT.
5. Снова открыть **«Резервные копии»** →
   - **«Экспорт логов»** — сохранить файл через выбор папки (SAF), затем
     передать файл, ИЛИ
   - **«Просмотр логов»** — открыть текст лога прямо в диалоге и скопировать
     содержимое.
6. Передать лог (файл или текст) для анализа — искать записи с тегом
   `AccentDebug`: они показывают, какая ветка `loadNameTogglesBody` сработала
   для каждого имени, что было прочитано/записано в БД, и в какой момент
   `saveCurrentNameToggles`/`loadNameToggles` реально захватывают блокировку.
7. После того как диагностика завершена, чекбокс «Записывать лог в файл»
   можно снова выключить (лог пишется в локальный файл на устройстве, за
   пределы устройства сам по себе не уходит, но продолжает расти, пока
   включён).

## Девятое исправление — настоящая корневая причина: битый Regex в `parseTickAccents`

Лог с устройства (`AccentDebug`, экспортирован пользователем) дал прямую
улику: в ветке `branch=USE_STORED` результат `parseTickAccents(storedAccentsJson)`
**всегда** оказывался равен `DEFAULT_TICK_ACCENTS` (5 акцентов
TICK/TOCK/BELL/CHIME/GONG) — даже когда `storedAccentsJson` на входе был
корректным JSON пресета «дерево жизни» (2 или 3 акцента WOOD/SOFT/…). Ветка
`HEAL_PRESET`, в отличие от неё, ВСЕГДА работала правильно — потому что она
берёт акценты напрямую из объекта `ACTIVITY_PRESETS`, а не парсит JSON.
Это и есть разгадка: проблема не в переключении имён, а в самом парсере.

**Причина:** в `parseTickAccents()` (`StopwatchViewModel.kt`, добавлена ещё в
коммите `2b15dc1` — при первом введении тикающих акцентов — и с тех пор ни
разу не менялась):

```kotlin
val pattern = Regex("""{"i":(\d+),"s":"([^"]+)"(?:,"o":(\d+))?}""")
```

Ведущая `{` и завершающая `}` не экранированы. В движке регулярных выражений
JVM (`java.util.regex.Pattern`, которым пользуется Kotlin `Regex`) голая `{`
всегда пытается открыть квантификатор повторения (`{n}`, `{n,m}`), и если
до соответствующей `}` не получается собрать валидный квантификатор —
бросается `PatternSyntaxException` уже на этапе компиляции самого паттерна.
Проверено локально на JVM (`java.util.regex`) с этим точным паттерном:

```
EXCEPTION: java.util.regex.PatternSyntaxException: Illegal repetition near index 1
{"i":(\d+),"s":"([^"]+)"(?:,"o":(\d+))?}
 ^
```

Эта ошибка происходит **на каждом вызове** `parseTickAccents` с непустым
JSON, сразу перехватывается внешним `catch (_: Exception) { DEFAULT_TICK_ACCENTS }`
— и функция молча возвращает дефолтные акценты, независимо от того, что было
реально сохранено в `accentsJson`. Функция была сломана с самого начала —
всё «случайное» поведение по всей цепочке исправлений 1–8 объясняется тем,
что баг маскировался HEAL_PRESET-веткой (шестое исправление), которая читает
акценты пресета напрямую из памяти, минуя сломанный парсер:

- если у имени сейчас `storedAccentsJson == defaultAccentsJson` — срабатывает
  HEAL_PRESET, показывает верно (не парсит JSON вообще);
- как только `storedAccentsJson` становится «настоящим», отличным от DEFAULT
  значением (после успешного хила или ручной правки) — следующая же загрузка
  идёт через USE_STORED → парсер ломается → тихий откат на DEFAULT → при уходе
  с имени это испорченное значение переписывается в БД как новое
  «истинное» → на следующей загрузке `storedAccentsJson == defaultAccentsJson`
  снова истинно → опять срабатывает HEAL_PRESET → выглядит как «само
  починилось» — отсюда и наблюдавшееся чередование OK/BROKEN.

Ни гонка (седьмое исправление), ни какая-либо логика переключения имён здесь
ни при чём. Это же объясняет и куда более старую историю бага (исправления
1–5): любой сохранённый в `session_names.accentsJson` набор акцентов,
отличный от DEFAULT, при следующей загрузке ЛЮБОГО имени (не только
пресетов) не мог быть корректно восстановлен из БД.

**Исправление:** экранированы `{` и `}` в паттерне:

```kotlin
val pattern = Regex("""\{"i":(\d+),"s":"([^"]+)"(?:,"o":(\d+))?\}""")
```

Проверено локально тем же способом (`java.util.regex.Pattern`) — с
экранированием паттерн компилируется и корректно находит все элементы
трёхэлементного JSON («дерево жизни» + ручная правка):

```
match: i=300 s=WOOD o=0
match: i=900 s=SOFT o=0
match: i=60 s=TICK o=0
total matches: 3
```

Другой код с тем же паттерном шаблонов в проекте не найден (`grep -rn
'Regex('` по `app/src/main/java/com/laplog/app/` — единственное вхождение).

Шестое (самовосстановление пресета) и седьмое (`nameSwitchMutex`)
исправления не откачены: они не вредны и остаются как дополнительный
защитный слой, даже когда корневая причина устранена. Диагностическое
логирование (`AccentDebug`, восьмой шаг) тоже оставлено на одну
дополнительную проверку — после подтверждения фикса на устройстве его
можно будет убрать.

**Статус: исправлено в коде, ждёт финальной проверки на устройстве** (тот же
сценарий 1–8, ожидаем, что на шагах 3 и 8 акценты больше не откатятся к
DEFAULT).

## Оставшиеся известные ограничения

### Проблема 1: ручной ввод имени не загружает акценты с сохранением предыдущего
`loadNameToggles` вызывается из `updateCurrentName` только при точном совпадении
с известным именем, но `saveCurrentNameToggles` для предыдущего имени НЕ
вызывается. Если пользователь изменил акценты, не переключив имя явно через
`selectNameFromHistory`, изменения могут не сохраниться для предыдущего имени.

**Сценарий:**
1. Имя «Бег», акценты A1. Пользователь меняет акценты, не нажимает «Сохранить».
2. Вручную стирает поле и набирает «Велик» → `loadNameToggles("Велик")` — без
   сохранения A1 для «Бег».
3. A1 сбрасывается. (Но в DB «Бег» хранит старый вариант A1 от предыдущего
   явного сохранения, так что деградация минимальна.)

### Проблема 2: первое переключение на имя без сохранённых акцентов показывает DEFAULT
После исправления 3 это стало предсказуемым поведением: имя без сохранённых
акцентов показывает DEFAULT и сохраняет их в DB. При последующих переключениях
пользователь видит то, что задал явно.
